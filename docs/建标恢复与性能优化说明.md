# 建标恢复与大视野性能优化（2026-10-15）

## 单图建标的新操作流程

直接点击“单图建标”选择原图即可，不需要先把标准图当作待测图加载。

遇到未找到圆点、超过 16 个候选点、ROI 过小、采样间对应不可靠或测量质量不合格时，程序会保留本次失败样图，打开“建标需要调整”窗口并选中 **ROI / 预览** 页。

1. 查看窗口提示的具体原因。左侧图像就是本次失败的建标图，不是上次待测图。
2. 拖框覆盖目标膜片全部圆点，给圆点边缘留出余量；必要时调整原图像素单位的半径范围。
3. 点击“预览当前参数”，核对圆点数量、轮廓、取色像素和质量提示。
4. 点击“使用当前参数继续建标”。程序重新校验所选采样，成功后才一起应用标准及参数。

取消时原标准、参数和待测结果保留。多图建标也使用这个恢复流程，调整后会重新检查全部所选图像，因此 ROI 应覆盖各次拍摄的全部目标圆点。

质量提示会区分定位/数量问题与曝光、反光、模糊、采样不足等原因。重新框选 ROI 不能修复真正的失焦或过曝，应重新采集合格标准图。文件打不开、运行库缺失等系统错误仍由主窗口报告，不把它们误导为 ROI 问题。

**数量限制**：未建立标准、也未指定实际点数时，算法无法知道“识别出 5 点但实际应有 7 点”。预览会明确提示人工核对是否完整；不能把少量几何和质量合格的候选自动证明为完整膜片。

## 性能瓶颈与改动

原多尺度实现会先对大量复杂背景轮廓求最小外接圆，再检查圆度。新相机全图中的膜片边缘和纹理轮廓点数很多，这个顺序造成显著开销。原生计时中的 `MeasurementMs` 包含候选筛选、精修和取色，并不只是求 Lab 均值。

- 在最小外接圆之前先检查面积、周长、圆度和包围框；这些都是原接受条件的必要条件，不改变判定阈值。
- 精修后的非圆区域先拒绝，再做局部 Lab 转换和质量统计。
- B/G/R 边缘分支用 OpenCV 线程池并行，结束后仍按 B/G/R 固定顺序合并，保持重复候选的优先级。
- 建标分析前后已经核验文件 SHA-256，创建标准时复用已核验哈希，避免第三次读取大 BMP。

本次没有关闭弱对比分支、减少尺度层数、放宽质量/色差门槛，也没有根据标准点数截断候选。默认半径仍为 8–500 px，Lab 仍取自原始像素。

## 性能测量

比较对象为本轮修改前后同机 Release DLL；同一图像、同一设置，预热 2 次、重复 12 次，记录中位数。下表为 `mc_analyze` 调用，包含读图、分割、精修和测量，不包含 WPF 绘制与报告生成。

| 固定场景 | 修改前 | 修改后 | 耗时减少 |
|---|---:|---:|---:|
| 旧相机五色图，全图 | 132 ms | 100 ms | 24% |
| 旧相机弱对比图，全图 | 126 ms | 96 ms | 24% |
| 新相机 JPEG，全图 | 1715 ms | 484 ms | 72% |
| 新相机 BMP，目标膜片 ROI | 172 ms | 150 ms | 13% |
| 新相机 BMP，全图 | 1658 ms | 592 ms | 64% |

新图为 5472×3648；BMP 的 ROI 为 x=1600、y=600、w=2400、h=2200。JPEG/ROI 目标为 7 点；全图 BMP 含周围膜片，输出 13 点，不应用“只留下 7 点”的方式提速。

这是当前机器与样本的测量值，不是所有电脑的节拍承诺。Debug 的未优化 C++ 和 Debug OpenCV 更慢，生产使用或速度评估请选 Release。宽范围搜索仍比只搜索已知尺寸花费更多时间；尺寸固定时可显式收窄范围并预览确认。

原始测量：`verification/roi-performance/before.json`、`channel-parallel.json`。入口为该目录的 `benchmark.py`。WPF 加载/离屏绘制使用 `tests/Verification/PerformanceBenchmarks.cs`，不等同于屏幕显示端到端延迟。

WPF 真实窗口入口也做了独立对照：固定读取旧相机上下两张图、计算并离屏绘制整个窗口，预热 2 次、重复 20 次，中位数 **355.9 → 283.5 ms（减少约 20%）**；P95 为 **430.9 → 313.3 ms**。已有结果的重复绘制仍约 13 ms，匹配及结果整理约 0.3 ms。原始记录为 `verification/performance-roi-before-Release.json`、`performance-roi-after-Release.json`。

## 源码与验证入口

已通过原项目 99 张、新图库 38 张和旧“条形膜片”144 张的预期点数回归（新 BMP 使用上述 ROI，JPEG 全图）。与修改前 DLL 的逐字段对照共 **281 张 / 833 点**，所有几何、Lab、采样数和质量数值完全一致，记录见 `verification/roi-performance/parity.json`。原生测试继续覆盖 8–500 px 半径、同帧混合尺寸及 ROI 坐标一致性。

- `StandardBuilder.cs`：强类型失败原因、保留失败样图、草稿重试与取消隔离。
- `MainWindow.Workflow.cs`：打开失败样图的 ROI 对话框，成功后提交标准与设置；ROI 变化时重新提取已有待测图。
- `SettingsWindow.xaml/.cs`：建标恢复模式、明确操作文案及点数/质量预览。
- `native/src/mark_detection.cpp`：廉价几何预筛、原分辨率精修后再测色。
- `native/src/mark_candidates.cpp`：分通道并行与确定顺序合并。
- `tests/Verification/StandardRecoveryTests.cs`：零点、20 点、过小 ROI、质量失败、取消及恢复预览。
- `verification/roi-performance/parity.py`：与前一便携包 DLL 比较全部数值字段，包括圆心、半径、Lab、采样数和质量指标。
